### F1: Day-one CORS verification is missing
- severity: major
- where: functional-spec.md:§3 In-Scope
- problem: The skeleton can pass every criterion without proving that the deployed origin can call GREEN-API.
- evidence: Architecture §3 explicitly requires checking CORS from `*.github.io` on day 1; serving a placeholder only verifies hosting and asset paths.
- fix: Add a manual acceptance check of a GREEN-API request from the deployed origin, including the required preflight, without adding login UI.

### F2: Passing checks are not required before deployment
- severity: major
- where: functional-spec.md:§2.2–§2.4
- problem: An accepted change could deploy despite failed lint, type checking, or tests. Running checks and publishing automatically does not establish a dependency between them.
- evidence: Merge restrictions are explicitly out of scope, and §2.3 tests only an unaccepted change that breaks the build.
- fix: Require deployment to depend on successful lint, typecheck, tests, and build for the same commit; test that a failed main-branch check preserves the previous deployment.

### F3: Latest-version guarantee contradicts failure recovery
- severity: minor
- where: functional-spec.md:§2.2 acceptance criteria
- problem: The unconditional requirement to show every accepted change within 10 minutes contradicts retaining the previous version when deployment fails. “Opens … within 10 minutes” also includes opening immediately after acceptance.
- evidence: §2.2 requires the new version, while §2.4 requires the previous version for a failed update.
- fix: Require a successfully checked and deployed change to become visible **no later than** 10 minutes after acceptance, explicitly excluding the failure case in §2.4.

### F4: Overlapping deployments have no ordering requirement
- severity: major
- where: functional-spec.md:§2.2
- problem: Two accepted changes can build concurrently, allowing an older, slower run to publish after a newer one. The spec does not define which version wins.
- evidence: Every accepted change triggers publishing, but there is no concurrency rule or acceptance case for overlapping runs.
- fix: Require that an older deployment cannot replace a newer deployed commit; add a test with two overlapping main-branch runs.

## Verdict

SHIP WITH FIXES

The spec needs deployment gating, ordering, and explicit day-one API verification before it reliably proves the delivery path.
