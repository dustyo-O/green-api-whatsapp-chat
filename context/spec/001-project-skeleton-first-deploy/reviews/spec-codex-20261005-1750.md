### F1: Concurrency does not guarantee deployment order
- severity: major
- where: technical-considerations.md:§2.7
- problem: Serializing workflows does not guarantee push order, so an older run can publish after a newer one.
- evidence: GitHub orders runs by when they start waiting, not dispatch time. Rerunning an older workflow also bypasses the assumed order. [GitHub concurrency documentation](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/control-workflow-concurrency)
- fix: Within the serialized workflow, reject deployment candidates older than the last successfully deployed revision; test an old-run rerun after a newer deployment.

### F2: The deployment-failure test cannot prove preservation
- severity: major
- where: technical-considerations.md:§2.8 and §4
- problem: Failing the first deployment with Pages disabled does not verify that a previous working page remains available.
- evidence: Functional §2.4 requires “the previous version's page”; the proposed test explicitly expects “nothing published.”
- fix: Keep the authorized bootstrap test, but add a deployment failure after a successful baseline and verify that baseline remains accessible with its original version.

### F3: The freshness criterion contradicts later deployments and caching
- severity: major
- where: functional-spec.md:§2.2; technical-considerations.md:§2.4
- problem: The criterion requires every accepted revision to remain visible at any time after ten minutes, even when superseded. The cache-busted verification also fails to test ordinary visitor freshness.
- evidence: If A and B are accepted one minute apart, both criteria demand different visible SHAs after eleven minutes. A cache lifetime starts when content is cached, not when a commit is accepted.
- fix: Define freshness for the latest successfully deployed, unsuperseded revision; separate deployment latency from cache propagation and verify normal navigation without cache busting.

### F4: The runtime requirement excludes supported-by-spec installations
- severity: minor
- where: functional-spec.md:§2.5; technical-considerations.md:§2.5 and §3 risk 7
- problem: The functional spec promises operation on Node.js 22 generally, while the selected toolchain requires 22.22.2 or later.
- evidence: `engines.node = ^22.22.2` contradicts “Anyone with … Node.js 22”; the assertion that older versions “still work” is unsupported by the stated dependency floor.
- fix: State “Node.js 22.22.2 or later within 22.x” consistently and run the clean-install acceptance check at that minimum.

### F5: Commit-format enforcement contradicts the accepted exception
- severity: minor
- where: functional-spec.md:§2.6; technical-considerations.md:§2.6
- problem: The functional requirement promises enforcement for every saved change, but the technical design deliberately leaves final main-branch commit messages unchecked.
- evidence: “A description that doesn't follow the format is refused” conflicts with “Push to main: not linted” and the explicitly accepted squash-title gap.
- fix: Amend §2.6 to limit enforcement to installed local hooks and PR commit ranges, explicitly documenting the accepted main/squash exception.

## Verdict
DO NOT SHIP

The deployment-order guarantee is unsupported, and the failure and freshness checks do not prove their stated acceptance criteria.
