### F1: Non-text bubbles and contact names contradict the closed scope
- severity: major
- where: functional-spec.md:§2.2–2.3
- problem: The spec adds non-text placeholder bubbles and WhatsApp contact names without updating the governing scope.
- evidence: Architecture §4 requires deleting and skipping media; product §3.2 excludes contact names from WhatsApp. Product §1.4 explicitly closes the feature list.
- fix: Remove these additions or explicitly amend the product definition and architecture before implementation.

### F2: Hidden-number chats have no identity or routing contract
- severity: major
- where: functional-spec.md:§2.2
- problem: A display-name fallback does not define how to identify a sender, merge subsequent replies, or send back to that chat.
- evidence: Architecture accepts personal chats identified by `@c.us`; the spec provides neither an identifier contract for hidden numbers nor rules preventing two unnamed senders from merging.
- fix: Define the supported payload and stable chat key, including reply capability; otherwise defer hidden-number support.

### F3: Exactly-once handling lacks partial-failure requirements
- severity: major
- where: functional-spec.md:§2.4
- problem: Reloading after successful receipt does not test the failure windows that can lose or duplicate a reply.
- evidence: Architecture requires durable storage before queue deletion. The spec does not cover storage failure, deletion failure, or a crash between those operations.
- fix: Require retaining the queue entry when persistence fails, safely retrying failed deletion, and deduplicating redelivery; add acceptance tests for those three cases.

### F4: Deferring tab coordination leaves a hole in the reliability guarantee
- severity: major
- where: functional-spec.md:§2.4 and §3 Out-of-Scope
- problem: The spec promises every reply exactly once while allowing multiple tabs to consume the same instance queue without coordination.
- evidence: One tab can acknowledge a reply that another never stores; concurrent localStorage writes can overwrite messages. Architecture specifies a single active poller to prevent this.
- fix: Make single-tab coordination a prerequisite, or explicitly limit Phase 1 acceptance to one tab and defer the broader guarantee.

### F5: Receiving recovery is undefined
- severity: major
- where: functional-spec.md:§2.4 and §3 Out-of-Scope
- problem: Deferring banners leaves unclear whether polling must recover from network errors, rate limits, and authorization loss in this phase.
- evidence: Architecture specifies polling backoff and automatic recovery, but all receiving acceptance tests assume successful requests.
- fix: Keep banners deferred while specifying polling recovery behavior and tests for network failure, 429 responses, and logout during an outstanding poll.

### F6: Delayed replies can produce the wrong sidebar order and preview
- severity: minor
- where: functional-spec.md:§2.2
- problem: Moving every arriving reply to the top and using it as the preview conflicts with chronological activity when queued replies arrive late.
- evidence: A queued 09:00 reply could replace a 10:00 outgoing message as the preview and outrank a chat active at 11:00.
- fix: Define preview and sidebar ordering by the latest stored message timestamp, and add a delayed-reply acceptance test.

### F7: Ten-second acceptance is broader than the product commitment
- severity: minor
- where: functional-spec.md:§2.1 and §2.4
- problem: The unconditional deadline includes offline periods and arbitrarily large queue backlogs.
- evidence: Product §1.4 limits latency measurement to normal broadband over five consecutive replies; this spec omits those conditions.
- fix: Adopt the product’s measurement conditions and distinguish live-reply latency from backlog recovery.

## Verdict
DO NOT SHIP

Resolve the scope conflicts and define identity, failure recovery, and concurrency behavior before implementation.
