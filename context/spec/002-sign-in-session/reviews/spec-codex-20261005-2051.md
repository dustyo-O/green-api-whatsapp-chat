### F1: Sign-in has no terminal state for unexpected failures
- severity: major
- where: functional-spec.md:§2.2
- problem: No timeout or fallback behavior is defined for HTTP 429/5xx, malformed responses, or unknown instance states. Sign-in and reload verification can remain stuck or produce an unspecified error.
- evidence: The error table covers credentials, connectivity and known setup problems; the only timing criterion requires successful sign-in within 5 seconds.
- fix: Define a request timeout and a recoverable fallback message that preserves inputs and enables «Проверить снова».

### F2: Late verification results can restore a logged-out session
- severity: major
- where: functional-spec.md:§2.4–§2.5
- problem: The spec does not invalidate pending verification when logout occurs. A tab checking saved credentials can finish after another tab logs out and persist the session again.
- evidence: Reload starts an asynchronous check; logout promises the browser forgets credentials. Cross-tab behavior is deferred without defining how this session lifecycle will respect logout.
- fix: Require logout to invalidate pending checks and prevent their results from restoring or persisting a session; add an acceptance test for this race.

### F3: Remembering credentials assumes storage always succeeds
- severity: minor
- where: functional-spec.md:§2.4
- problem: There is no behavior for unavailable localStorage, failed writes, or unreadable saved data. QA cannot determine whether sign-in should fail, continue temporarily, or recover to an empty form.
- evidence: The spec unconditionally promises remembered sessions; the architecture requires localStorage persistence.
- fix: Specify recovery to the sign-in form for invalid saved data and an explicit nonpersistent-session message when saving fails.

### F4: API URL validation admits unusable addresses
- severity: minor
- where: functional-spec.md:§2.1
- problem: Checking only the `https://` prefix accepts values such as `https://` and leaves URL path/query handling undefined. Automatic derivation for fewer than four instance digits is also unspecified.
- evidence: The button requires only a prefix, while the architecture explicitly requires the derived URL to remain empty until four digits are entered.
- fix: Require a parseable HTTPS base URL, define permitted path/query components and trailing-slash normalization, and add the four-digit derivation threshold.

## Verdict

SHIP WITH FIXES

Define failure recovery, pending-check invalidation, storage failure behavior and URL validation before implementation.
