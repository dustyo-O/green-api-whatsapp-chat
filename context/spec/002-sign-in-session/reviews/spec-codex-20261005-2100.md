### F1: Accepted API URLs can break request construction
- severity: major
- where: technical-considerations.md:§2.4 URL validation
- problem: Validation accepts query strings and fragments, but the client appends API paths directly to the supplied string. Valid form input can therefore produce requests to the wrong endpoint.
- evidence: `https://example.com/#x` passes validation; appending `/waInstance…` puts the API path in the fragment, which is never sent.
- fix: Reject query strings, fragments and userinfo; define whether base paths are supported and test URL construction accordingly.

### F2: Missing settings can incorrectly pass readiness checks
- severity: major
- where: technical-considerations.md:§2.2 outcome mapping
- problem: Treating an absent `webhookUrl` as empty allows an incomplete response to establish readiness without evidence that webhook delivery is disabled.
- evidence: `{ "incomingWebhook": "yes" }` passes the stated readiness rules, despite the separate rule mapping wrong-shape responses to `unknown`.
- fix: Require a present, valid `webhookUrl` value; map missing or malformed values to `unknown`. Explicitly document any verified nullable representation.

### F3: Storage failures have no defined operational fallback
- severity: major
- where: technical-considerations.md:§2.3 Session store
- problem: The store assumes persistence succeeds. A storage write exception can interrupt sign-in or logout; excluding a save-failure message does not define how these actions complete.
- evidence: Zustand persistence accompanies state updates, while the only specified storage recovery covers unreadable saved data.
- fix: Define and test exception-safe storage handling: preserve usable in-memory state, complete logout, and avoid claiming persistence when saving fails.

### F4: Successful checks between five and fifteen seconds are unspecified
- severity: minor
- where: functional-spec.md:§2.2 acceptance criteria
- problem: The happy-path criterion requires entry within five seconds without controlling API latency, while the check permits fifteen seconds. QA cannot determine whether an eight-second successful response is acceptable.
- evidence: “within 5 seconds” versus “no answer within 15 seconds.”
- fix: Make five seconds a measured target under stated conditions, and explicitly accept successful checks completed before the fifteen-second deadline.

## Verdict
SHIP WITH FIXES

Resolve URL construction, readiness validation and storage failure handling before implementation, and clarify the timing criterion.
