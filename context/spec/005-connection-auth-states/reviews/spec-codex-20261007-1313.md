### F1: Authorization detection has no trigger or deadline
- severity: major
- where: functional-spec.md:§2.3
- problem: “When GREEN-API reports” leaves authorization monitoring unspecified. An implementation could check only at login and never detect a later logout.
- evidence: The architecture schedules `getStateInstance` only at login and reload; the spec adds no periodic check or notification contract.
- fix: Define the authorization detection mechanism, maximum detection delay, and recovery checks while sending is paused.

### F2: The three-second connection deadline is not enforceable as written
- severity: major
- where: functional-spec.md:§2.2
- problem: Two failed receive attempts have no defined timeout or starting point for the three-second deadline. A connection that stalls without a device-offline event could leave sending enabled indefinitely.
- evidence: The architecture uses approximately 20-second long polls; a dropped connection need not reject `fetch` immediately.
- fix: Distinguish device-offline detection from unreachable-service detection, and specify request deadlines and a measurable detection bound for each.

### F3: Error classification cannot reliably distinguish an invalid key
- severity: major
- where: functional-spec.md:§2.2–§2.5
- problem: The spec requires distinct banners without defining which responses establish each condition. A replaced key may produce an ambiguous network failure instead of the promised access-key banner.
- evidence: The architecture explicitly says fetch-level failures can represent offline conditions or CORS-less error pages, and groups 401/403 under “credentials invalid / instance not authorized.”
- fix: Specify verified response-to-state mappings, including an ambiguous-failure fallback; make the replaced-key acceptance criterion match the observable API behavior.

### F4: Send blocking omits retries and requests already in flight
- severity: major
- where: functional-spec.md:§2.6
- problem: Acceptance criteria cover Enter but leave manual retry and pending sends undefined. A send accepted after authorization is lost could still gain the misleading checkmark the overview promises to prevent.
- evidence: The product includes manual retry, and the architecture distinguishes accepted sends from uncertain outcomes using `unknown`.
- fix: Apply the pause guard to every send entry point, including retry, and specify how pending responses are handled; narrow the checkmark guarantee to what the API can establish.

### F5: Non-authorized instance states have no runtime behavior
- severity: major
- where: functional-spec.md:§2.3
- problem: Only a WhatsApp logout is covered. QA cannot determine the banner, send availability, or recovery behavior for an instance that becomes blocked, suspended, starting, or asleep.
- evidence: The architecture explicitly recognizes `blocked`, `sleepMode`, `starting`, and `suspended`, and requires `authorized` at login.
- fix: Define runtime handling and recovery for every recognized instance state, with appropriate guidance instead of universally prescribing a QR scan.

### F6: “Receiving stuck” leaves acknowledgement failures undefined
- severity: major
- where: functional-spec.md:§2.5
- problem: It is unclear whether receiving succeeds when a notification is fetched or only when it is handled and deleted. Repeated successful fetches with failed deletes could prevent later replies indefinitely without showing a banner.
- evidence: The architecture defines receiving as a sequential receive → handle → delete cycle; the criterion only refers to GREEN-API answering “normally.”
- fix: Include failed acknowledgements in the stuck condition and define exactly which successful operation resets the one-minute timer.

## Verdict
DO NOT SHIP

Detection, error classification, and send-state rules remain too undefined to implement and test the promised behavior reliably.
