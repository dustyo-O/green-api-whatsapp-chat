### F1: Recovery can exceed the 10-second limit
- severity: major
- where: technical-considerations.md:§2.2
- problem: The recovery bound assumes an `online` event, but an upstream outage can recover without one.
- evidence: An outstanding request can consume its remaining 8-second budget, followed by 5-second backoff and a 5-second empty poll: up to 18 seconds.
- fix: Adjust request and retry timing to meet 10 seconds without an `online` event, and test that path.

### F2: One failed state check breaks the authorization guarantee
- severity: major
- where: technical-considerations.md:§2.1–2.2
- problem: The four-minute watch does not guarantee detection or recovery within five minutes when a check fails.
- evidence: Watch timeouts, 429s and 5xx responses are ignored; the next attempt comes four minutes later. With state notifications disabled, detection can exceed eight minutes.
- fix: Retry failed checks within the remaining detection budget, and qualify the guarantee for periods when the state endpoint cannot be reached.

### F3: The stuck banner has no reliable one-minute deadline
- severity: minor
- where: technical-considerations.md:§2.2
- problem: The banner is raised only by a subsequent failure, so it need not appear after one minute as required.
- evidence: The technical spec explicitly permits 60–65 seconds; its assertion that failures repeat every five seconds also excludes request duration.
- fix: Start a cancellable 60-second timer on the first qualifying failure; cancel it only when receiving works or the session ends.

### F4: A pending new-chat request bypasses the pause
- severity: major
- where: technical-considerations.md:§2.4
- problem: Checking the paused state only on form submission allows an outstanding `checkWhatsapp` request to create a chat after a pausing banner appears.
- evidence: The functional spec forbids starting chats while paused and grants an in-flight exception only to sends.
- fix: Recheck the paused state after `checkWhatsapp` resolves and before creating or opening the chat; preserve the form input.

### F5: The logged-out response probe lacks a disambiguation rule
- severity: major
- where: technical-considerations.md:§3, risk 1
- problem: If receiving returns the same 4xx for logout and invalid credentials, adding an `auth` mapping cannot distinguish the two required banners.
- evidence: §2.2 maps 401/403 to `keyInvalid`; risk 1 proposes mapping a logged-out 4xx to `auth` without specifying distinguishable evidence.
- fix: Probe both conditions first. If their responses overlap, use `getStateInstance` to disambiguate and define behavior when that check fails.

## Verdict
DO NOT SHIP

The draft leaves recovery deadlines and authorization classification unresolved, and permits chat creation while paused.
