### F1: A stale number check can create a chat in another session
- severity: major
- where: technical-considerations.md:§2.6 NewChatForm
- problem: A WhatsApp check started before logout can finish after another sign-in and add its result to the new instance’s store.
- evidence: The flow awaits `checkNumber` then calls `addChat`; the only session guard is `idInstance === null`, which no longer holds after another sign-in.
- fix: Capture a session generation before the request and discard the result if that generation changes.

### F2: Persistence failures have no defined behavior
- severity: major
- where: technical-considerations.md:§2.4 Persist and Size
- problem: A full or unavailable localStorage can interrupt sending or lose drafts and messages without a specified recovery state.
- evidence: Every mutation writes synchronously; storage has “no cap, no pruning,” and no handling is defined for write failures.
- fix: Catch persistence failures, show a persistent storage-error message, and define whether sending is blocked or continues without reload guarantees.

### F3: Oversized messages are knowingly classified as uncertain sends
- severity: major
- where: technical-considerations.md:§2.1–§2.2 sendMessage
- problem: The composer accepts messages beyond the documented limit, then labels the documented payload-too-large response as an unknown outcome and offers another identical attempt.
- evidence: The contract specifies “≤ 20 000 chars” and “500 (payload too large),” while all 5xx map to `unknown`.
- fix: Reject oversized text before sending, preserve the draft, and show the limit; add boundary acceptance tests.

### F4: Invalid numbers lack the product’s required specific error
- severity: major
- where: technical-considerations.md:§2.2 checkNumber
- problem: Invalid-number responses become a generic retry message. The proposed alternative incorrectly equates malformed input with a valid number that lacks WhatsApp.
- evidence: Product §1.4 requires a specific invalid-phone message; the mapping collapses `400 Bad phone number` into `checkFailed` and suggests changing it to `notOnWhatsapp`.
- fix: Add an `invalidNumber` outcome with a specific correction message and acceptance criterion.

### F5: The persisted message contract contradicts the architecture
- severity: minor
- where: technical-considerations.md:§2.4 Message; architecture.md:§2 Persisted Data
- problem: The technical spec introduces `unknown` and a local millisecond timestamp without reconciling the architecture’s status enum and GREEN-API timestamp contract.
- evidence: Architecture persistence permits only `sending | sent | failed`; the new store uses `sending | sent | failed | unknown` and `time (epoch ms)`.
- fix: Update the architecture to include `unknown` and explicitly distinguish local outgoing time from provider timestamps, including their units.

### F6: Sending silently strips intentional whitespace
- severity: minor
- where: technical-considerations.md:§2.6 Composer
- problem: Sending trims leading and trailing spaces and newlines, although the functional spec only excludes whitespace-only messages.
- evidence: The implementation sends `text.trim()`; functional §2.3 requires the entered text and multiline content to appear in the bubble.
- fix: Use trimming only to test emptiness, then send and display the original text.

## Verdict

SHIP WITH FIXES

Resolve session isolation, persistence failures, and input-error handling before implementation, and align the documented message contracts.
