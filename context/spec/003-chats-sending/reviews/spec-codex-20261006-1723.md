### F1: Phone entry changes the agreed validation contract
- severity: major
- where: functional-spec.md:§2.1
- problem: The spec replaces international-number input with national-number input and removes the architecture’s 10–15-digit validation. Custom country-code validation is also undefined.
- evidence: The product accepts a leading `+`; the architecture requires 10–15 digits. This spec enables submission with one digit and explicitly imposes no length check.
- fix: Preserve international-number input and validate the final normalized number as 10–15 digits, including any custom country code.

### F2: Mandatory WhatsApp lookup adds an unspecified dependency
- severity: major
- where: functional-spec.md:§2.1 and §3
- problem: Chat creation now depends on an additional API operation absent from the closed product scope and architecture. Its request, response, timeout, and error mapping are unspecified.
- evidence: Previously chat creation required number normalization; now “the app first checks that the number uses WhatsApp,” and lookup failure blocks creation.
- fix: Remove the mandatory lookup from this phase, or explicitly amend the product and architecture with its API contract and failure tests.

### F3: Interrupted sends are incorrectly presented as confirmed failures
- severity: major
- where: functional-spec.md:§2.3–§2.4
- problem: A timeout or reload can occur after GREEN-API accepts a message. Labeling that message “Не отправлено” and offering retry can produce duplicate delivery.
- evidence: Every message still showing 🕓 becomes failed after reload, regardless of whether the server accepted it.
- fix: Distinguish confirmed rejection from unknown delivery status; label interrupted sends as uncertain and explain that manual retry may duplicate the message.

### F4: Draft persistence is missing from the reload contract
- severity: major
- where: functional-spec.md:§2.3–§2.4
- problem: The spec does not define whether unsent text survives chat switching or reload, despite the architecture requiring persisted drafts per chat.
- evidence: Architecture §2 lists “Drafts: the unsent text per chat”; this spec only promises persistence for chats and messages.
- fix: Require per-chat drafts to survive switching and reload, clear on logout, and add an acceptance criterion.

### F5: Pending lookup behaviour permits conflicting chat creation
- severity: minor
- where: functional-spec.md:§2.1
- problem: There is no pending state or rule for repeated submissions and edits while a WhatsApp lookup is running. Delayed responses could open the wrong chat or create duplicates.
- evidence: The button is governed only by input validity; no acceptance criterion covers an outstanding lookup.
- fix: Disable duplicate submission while checking, bind results to the submitted normalized number, and ignore stale results after input changes or logout.

### F6: Empty-chat presentation and sorting are undefined
- severity: minor
- where: functional-spec.md:§2.2–§2.3
- problem: Newly created chats have no last message or message time, and the right pane has no specified state before a chat is selected.
- evidence: Every list item must show its “last message” and time, while new empty chats must appear at the top. The product separately requires an empty state with no selection.
- fix: Specify blank preview/time for empty chats, use creation time until first activity for sorting, and define the no-selection placeholder.

### F7: The sent indicator has no precise success condition
- severity: minor
- where: functional-spec.md:§2.3
- problem: “Once it's sent” can mean API acceptance or recipient delivery, making the status criterion ambiguous.
- evidence: The product explicitly defines sent as GREEN-API acceptance; this spec couples ✅ with wording that the message “went out” and real-phone arrival.
- fix: Define ✅ as a successful `SendMessage` response containing `idMessage`; keep recipient arrival as a separate manual acceptance check.

## Verdict

DO NOT SHIP

The draft changes agreed contracts and leaves ambiguous send outcomes and required persistence behaviour unresolved.
